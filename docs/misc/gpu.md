# How to think about GPUs

读 JAX Scaling Book 的 [How to Think About GPUs](https://jax-ml.github.io/scaling-book/gpus/#what-is-a-gpu) 时，一个很有帮助的视角是：

**把 GPU 想成“一大块高带宽内存（HBM）+ 很多可以并行工作的计算单元（SM）”。**

以 H100 为例，一张卡上有 132 个 SM（Streaming Multiprocessor）。每个 SM 内部又有几类关键部件：

- **Tensor Core**：负责矩阵乘法，是大模型训练和推理的主力。
- **CUDA Core / Warp Scheduler**：负责向量运算、逐元素计算、归约等。
- **SMEM / L1**：片上高速缓存，适合临时存放被重复使用的数据。

## 一个更实用的理解方式

如果只记一句话，那就是：

> GPU 不是单个“超级核心”，而是很多相对独立的小核心，在一起吞吐大规模并行任务。

这也解释了为什么 GPU 很适合深度学习：

1. 模型里有大量矩阵乘法；
2. 同样的计算可以在很多 token、样本、head、channel 上并行展开；
3. 只要把足够多的工作同时喂给 GPU，它就能把吞吐拉起来。

## 影响性能的几个关键词

### 1. 并行度

GPU 喜欢“大批量、可并行”的工作。  
如果只提交很小的一点任务，很多 SM 会闲着，性能就上不去。

### 2. Tensor Core 利用率

在大模型场景里，真正值钱的通常是 Tensor Core 的利用率。  
越能把计算组织成规则的大矩阵乘法，越容易接近峰值性能。

### 3. 内存层级

GPU 的内存不是一层，而是分层的：

- 寄存器（最快，最小）
- SMEM / L1
- L2
- HBM（最大，但相对更慢）

很多性能问题，不是算得不够快，而是**数据没有及时送到计算单元**。  
所以优化时要特别关注数据复用、访存模式和带宽。

### 4. Warp divergence

Warp 可以理解为一组一起执行的线程。  
如果同一个 warp 里的线程走了不同分支，GPU 往往需要把不同路径都跑一遍，只是屏蔽掉一部分线程，这会让效率下降。

所以 GPU 通常更喜欢规则、整齐、分支少的计算。

## GPU 和 TPU 的一个直觉区别

JAX Scaling Book 里还提到一个很重要的对比：

- **TPU** 更像少量但很大的核心，结构更规则；
- **GPU** 更像大量更灵活的模块，适应性更强，但也更难推到极致性能。

因此，GPU 常常“更容易跑起来”，但想跑到很好，仍然需要理解：

- 任务有没有铺满 SM；
- Tensor Core 有没有吃饱；
- HBM 和缓存有没有成为瓶颈；
- 程序有没有过多分支和同步。

## 总结

理解 GPU 的关键，不是死记硬背参数，而是建立下面这个心智模型：

> **GPU = 面向吞吐优化的大规模并行系统。**

写程序时，要不断问自己：

1. 我是不是给了它足够多的并行工作？
2. 我是不是把计算组织成了 GPU 喜欢的矩阵乘法？
3. 我是不是被访存和分支拖慢了？

带着这个问题去看训练、推理、并行策略和 profiling 结果，会更容易理解为什么代码跑得快或慢。
